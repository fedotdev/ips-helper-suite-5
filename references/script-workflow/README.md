# Разработка скриптов Workflow (действие «Сценарий») в IPS 9.x

Практические выводы из разработки скрипта создания **поручения на разработку ТД**
(`D:\IPS\Scripts\СозданиеПорученияТД.cs`). Область применимости: скрипты действия
«Сценарий», которые создают объекты, связи и/или запускают процессы, особенно
объекты **канцелярского документооборота** (поручения).

Проверено на IPS **9.0.4 (9.0.4.11310)**.

---

## 1. Главное правило: канцелярию/офис инициализирует сам IPS

Если скрипт создаёт объект типа семейства «Документы» / «Канцелярские документы»
(в т.ч. **поручение**), то `CommitCreation()` запускает офисную подсистему
`Intermech.Office.Server`. Ошибки из неё — это **не дефект скрипта**, а
конфигурация (шаблоны и переменные процессов), которую скрипт не создаёт.

Признак: стек начинается/содержит `Intermech.Office.Server.*`, а не ваш код:

```
Intermech.Office.Server.DBResolution.Run()
  -> DBResolution.DoCommitCreation()
    -> Intermech.Kernel.DBObject.CommitCreation(...)
      -> ... -> Script.Execute(IActivity activity)
```

Стек читать **снизу вверх**: последняя строка (`Script.Execute`) — где стартовали,
верхние строки (`DBResolution`, `ResolutionProcess`) — что упало по пути.

## 2. Типовые ошибки и их причина

| Сообщение / исключение | Где искать причину | Лечение |
|---|---|---|
| «В настройках канцелярии не выбран шаблон для контрольных поручений параллельного исполнения поручений без документов» | Настройки канцелярии типа документа | Задать шаблон процесса для нужной **категории** (см. §3) |
| `Intermech.Office.Interfaces.VariableMissingException` «Процесс не содержит переменную `COMMISSION_AUTHOR`» | Шаблон процесса | Добавить в шаблон недостающие переменные (см. §3) |
| `ObjectAttributeValueIsEmptyException` в `DBResolution.GetActualSeeingUserIDsEnum(executorIDs)` | Обязательный атрибут поручения пуст | Заполнить обязательные атрибуты, прежде всего «Исполнение поручения» (см. §5, §6) |
| Ошибка присвоения `374` при `Values = ...` | Тип ссылки не совпал | Ссылочный атрибут принимает объект **другого** типа (напр. в «Исполнители поручения» — только пользователи, не должности) |
| `Intermech.Workflow...MessageCommandProvider.SendTo` в самом низу стека | Запуск действия пользователем | Это точка входа, не причина |

Важно: сообщение о категории («параллельного исполнения») офис формирует из значений
атрибутов поручения, даже если сам атрибут ещё пуст. Поэтому «параллельное» в тексте
ошибки ≠ атрибут «Исполнение поручения» заполнен.

## 3. Категория поручения и штатные шаблоны процессов

Категория складывается из трёх признаков:

- **контрольное / неконтрольное** (атрибут «Контрольное поручение», логический);
- **параллельное / последовательное / комбинированное** (атрибут «Исполнение поручения», целое);
- **с документами / без документов**.

Для каждой категории в «Настройках канцелярии» типа документа назначается **шаблон
процесса** (шаблоны заданы по умолчанию для типа «Документы» и наследуются дочерними —
см. «Руководство администратора», п. 5.6.1).

Штатные шаблоны (тип 1133 «Шаблоны процессов»), найдены в базе:

| Категория | Шаблон | objectId шаблона |
|---|---|---|
| контрольное + параллельное | Шаблон процесса для контрольного поручения | 1008870 |
| контрольное + последовательное | Шаблон процесса для последовательного контрольного поручения | 1114520 |
| неконтрольное + параллельное | Шаблон процесса для неконтрольного поручения | 1008854 |
| неконтрольное + последовательное | Шаблон процесса для последовательного неконтрольного поручения | 1114572 |

**Обязательные переменные шаблона поручения** (точные имена, заглавные, без пробелов):

| Переменная | GUID (системный атрибут) | id |
|---|---|---|
| `COMMISSION_USER` | `cadd9301-306c-11d8-b4e9-00304f19f545` | 15331 |
| `PLANNED_DATA` | `cadd9302-306c-11d8-b4e9-00304f19f545` | 15332 |
| `CONTROL_USER` | `cadd9303-306c-11d8-b4e9-00304f19f545` | 15333 |
| `COMMISSION_AUTHOR` | `cadd9304-306c-11d8-b4e9-00304f19f545` | 15334 |

Если назначен **свой** шаблон — скопируйте в него переменные из штатного (свойства
шаблона → «Переменные»). Имена регистрозависимы. Проверить наличие переменных по
метаданным **нельзя**: `COMMISSION_*` — глобально применимые атрибуты (ftMemo),
числятся за всеми шаблонами с пустыми значениями; MCP их «видит» у любого шаблона.

Аналогично для других процессов канцелярии: шаблон отправки письма должен содержать
те же переменные и скрипт, что штатный (п. 5.6.2); шаблон уведомления адресатам —
переменную `ADDRESSEE` (п. 5.6.3).

## 4. Метаданные: как быстро получить id / GUID / допустимые значения

### 4.1 `gloss.db` — оффлайн-выгрузка
Путь: `D:\IPS\IPS-MCP\gloss\generated\gloss.db` (SQLite). Таблицы:
`object_types`, `attribute_types`, `relation_types`, `metadata`, `object_type_attributes`
(пустая), `relation_applicability`, `validation_errors`.

Что можно взять: `id`, `name`, `guid`, `data_type`, `size_type`, комментарии.
Чего **нет**: списка допустимых значений («из списка» — только текст-описание),
состава атрибутов типа (таблица пуста).

Читать через Python `sqlite3`, результат писать в файл **UTF-8** и читать его:
консоль PowerShell в cp1251 искажает русские имена.

```python
import sqlite3, json
c = sqlite3.connect(r"D:\IPS\IPS-MCP\gloss\generated\gloss.db")
cur = c.cursor()
cur.execute("select id, name, guid from object_types where name like '%оручен%'")
print(cur.fetchall())
```
*Осторожно с курсором:* `PRAGMA table_info(...)` через тот же курсор **сбрасывает**
результат незавершённого `select` — сначала получайте колонки, потом `execute`.

### 4.2 MCP (`ips` в opencode)
- `ips_get_attribute_type(id)` — **единственный** надёжный источник допустимых
  значений: поля `possibleValues` и `possibleValuesDescriptions`. Пример для
  «Исполнение поручения» (17467): `[0,1,2]` = Параллельное / Последовательное /
  Комбинированное.
- `ips_get_object_type(id)`, `ips_search_objects(...)`, `ips_get_object_attributes(...)`.

### 4.3 Особенности API поиска
- `IDBObjectCollection.Select(DBRecordSetParams)` — фильтр по атрибутам через
  `ConditionStructure(attrId, RelationalOperators.Equal, value, LogicalOperators.NONE, 0, false)`.
- MCP `ips_search_objects` **не фильтрует по ссылочным атрибутам** (возвращает все
  объекты) → для подбора по ссылке в скрипте используйте `Select` + `ConditionStructure`.
- `F_OBJECT_ID` из `Select` = **id версии**, а не objectID. Проверено: совпал со
  значением ссылки на пользователя. Для карточки — `session.GetObject(versionId)`.

## 6. Правильная последовательность создания поручения в скрипте

```
1. Определить документ-основание (activity.Attachments[0].Object).
2. Получить исполнителей-пользователей (резолв должностей — см. §7).
3. objects.Create(); // по типу «Поручения»
4. Заполнить обязательные атрибуты:
   - Текст поручения
   - Исполнители поручения        (.Values = object[] ссылок на версии)
   - Автор                        (= session.UserID)
   - Контрольное поручение        (true)
   - Контролёр                    (= session.UserID) — обязателен для контрольного
   - Плановая дата исполнения     (.AsDateTime) — НЕ «Дата контроля»
   - Исполнение поручения         (.AsInteger = 0) — обязательно (см. ниже)
5. res.CommitCreation(true);      // здесь и стартует офисная подсистема
6. session.GetRelationCollection(RelKanc).Create(doc.ObjectID, res.ObjectID);
7. Присвоить атрибут процесса «Идентификатор поручения» = res.ObjectID.
```

Ключевые факты (Руководство пользователя, п. 14.3):

- При **первом** присвоении «Плановой даты исполнения» система сама добавляет признак
  **контрольного** и ставит **Контролёром автора** поручения.
- «Исполнение поручения» — **обязательный** атрибут. Если оставить пустым, офисный
  расчёт «видящих пользователей» падает с `ObjectAttributeValueIsEmptyException`.
  Значение `0` = Параллельное.
- «Дата контроля» вводится контролёром **после** ознакомления с отчётами — не
  заполнять при создании.
- Поручение после создания автоматически запускает процесс по шаблону категории.

## 7. Резолв «должность → пользователи»

Должности нельзя писать в «Исполнители поручения» (там только «Пользователи» → ошибка
374). Связь «пользователь → должность» хранится в атрибуте **«Должность»** у типа
«Пользователи»:

| Что | id | GUID |
|---|---|---|
| Тип «Пользователи» | 1 | `cad00002-306c-11d8-b4e9-00304f19f545` |
| Тип «Должности» | 1010 | `cad00147-306c-11d8-b4e9-00304f19f545` |
| Атрибут «Должность» (у пользователя) | 1044 | `cad00142-306c-11d8-b4e9-00304f19f545` |

Пользователи искомой должности берутся через `Select` по «Пользователи» с условием
`Должность = positionId` (см. §4.3). Значение переменной процесса может прийти в разных
видах — ссылка на объект, число, строка (`"123.0"`), список, XML участников
(`<Participants><Rank><ID>92622</ID></Rank></Participants>`) — парсер должен
обработать все варианты и собрать все `<ID>`.

## 8. Развёртывание и отладка в IPS

1. Скрипт вставляется как действие **«Сценарий»**; исполнитель действия — «Инициатор
   процесса» (или конкретный пользователь перехода), иначе сценарий не выполнится.
2. Скрипт **компилируется сервером** при выполнении (в стеке видно
   `Script_<guid>_<n>.dll`). Локально собрать нельзя — проверка только на копии базы.
3. Скрипт **пишет в БД** (создаёт объект и связь) → тестировать на **копии** базы.
4. После правки шаблона: **Сохранить**, при необходимости — новая версия, **снять с
   отладки** («Закончить отладку»). Редактор шаблонов (в WebInterface — меню
   «Настройка / Редактор шаблонов процессов»).
5. **Уже запущенные** процессы не подхватывают изменённый шаблон — перезапустить.
6. Вносите правки сразу во **все** нужные категории шаблонов (напр. и в параллельное,
   и в последовательное контрольное поручение), иначе ошибка вернётся на другой
   категории.

## 11. Пайплайн: чтение и правка скрипта-объекта через MCP/API

Скрипт действия «Сценарий» — не файл, а объект базы:

| Что | Значение |
|---|---|
| Тип объекта | `1889` «Локальные сценарии маршрутизатора» (`cadd996d-...`) |
| Код скрипта | атрибут `1324` «Текст сценария» (`ftMemo`) |
| Имя объекта | системный `caption` |

Шаги:

1. Найти объект: в шаблоне процесса открыть действие «Сценарий» → его id
   (пример: шаблон `1412434`, сценарий `1412445`).
2. `ips_get_object(id)` → `objectType`, `caption`, `readOnly`, `lcStep`, `ownerID`.
3. `ips_get_object_attributes(id)` → взять атрибут `1324`; имя атрибута сверить с
   `gloss.db` (`attribute_types`), т.к. в выдаче бывает только id.
4. Правка — только парой preview → commit:
   `ips_prepare_update_attribute(id, 1324, "<новый текст>")` → проверить diff →
   `ips_commit_update_attribute(request_id)`.
   Внутри: `checkOut` → `edit` → `POST /attributes` → `saveChanges` → `checkIn`;
   при ошибке — `cancelChanges`.
5. Проверка: повторно `ips_get_object_attributes(id)` — текст совпал, версия выросла.

### Название создаваемого поручения

`caption` объекта берётся из атрибута, указанного в `captionAttributeId` типа:

- `ips_get_object_type(1631)` → `captionAttributeId: 10`;
- атрибут `10` «Наименование» (`cad00020-...`, Строка, 450);
- в скрипте задавать через `Attributes.AddAttribute(AttrCaption, false).Value = ...`,
  а не `res.Caption` (caption — производное от атрибута);
- записью через API не проверено (упёрлись в ACL) — проверять на копии базы.

### Роль для записи

Запись под ролью **`775358` «Репликатор баз данных»** (`isAdmin: true`) — проверено
на объекте `1412445`: `checkOut` → `edit` → `saveChanges` → `checkIn` прошли,
`workingCopyId: -1412445` (отрицательный id — рабочая копия основной версии, норма).
После `checkIn` текст в базе совпал с локальным, `versionsCount` не изменился,
`readOnly`/`lcStep` остались прежними.

Роль по умолчанию `782041` прав на объект-скрипт не имеет. Роли задаются в
`config.json`: `IPS_ROLE_TECHNO_ID` (чтение) и `IPS_ROLE_PROG_ID` (запись).
Переключение без перезапуска — `ips_set_role` с `{"role": "prog"}`; проверка —
`ips_get_current_user` → `roleVersionId` равен `IPS_ROLE_PROG_ID`.

### Типичные блокеры

- `checkOut` → **«у сервисного аккаунта нет прав на объект (id=...)»** — это ACL
  роли сервисного аккаунта MCP, а не lifecycle и не `readOnly`. Переключиться на
  роль `775358` либо выдать права.
- `401` + «JWT refresh-токен не является корректным» — в `ips.py` при 401 нужен
  fallback `_refresh` → `_authenticate`; уже запущенный MCP-процесс держит старые
  токены, нужен перезапуск.
- `readOnly: true` / `lcStep` — отдельная причина отказа; сообщение про права и
  сообщение про жизненный цикл различать.

### Standalone-обход MCP-процесса

Если MCP-сервер завис на старых токенах, читать/писать можно тем же клиентом из
отдельного процесса:

```python
import sys; sys.path.insert(0, r"D:\IPS\IPS-MCP\src")
from ips_mcp import ips
client = ips.IpsClient(base, login, password, role_id=role)
obj   = client.request("GET", f"/core/api/objects/{oid}").get("entity")
attrs = client.request("GET", f"/core/api/objects/{oid}/attributesValues")
ips.write_attribute(client, oid, 1324, new_text)  # checkout→edit→save→checkin
```

`write_attribute` при ошибке сам делает `cancelChanges`, но ACL он не обходит.
