# Производительность C# в IPS 9.x

Читайте этот файл при ревью C#-кода, жалобах на медленный сценарий, массовой обработке,
генерации больших документов и запросах «оптимизируй». Его цель — не применить максимум
современных приёмов .NET, а убрать реальное узкое место, не нарушив модель выполнения IPS.

## 1. Сначала определите профиль выполнения

Не предлагайте код, пока не установлен хотя бы один профиль:

| Профиль | Подтверждённая среда | Главные ограничения |
|---|---|---|
| Сценарий C# / Script Pad | Код компилируется IPS на лету и выполняется внутри клиента или сервера | Нельзя фоновые потоки, `ThreadPool`, `Timer`, `Task`, `async/await`, `BeginInvoke`/`EndInvoke`, Parallel LINQ, подписки на события и изменяемые статические поля |
| Серверный модуль IPS SDK 9+ | Примеры SDK используют `net6.0` | Только специальные шаблоны IPS SDK; асинхронность допустима лишь там, где конкретный IPS API и жизненный цикл модуля это поддерживают |
| Клиентский модуль / COM API | Примеры SDK используют `net48` | Не переносить API и синтаксис новых версий .NET без проверки проекта |
| Общая библиотека SDK | В примерах встречается `netstandard2.0` | Соблюдать совместимость всех потребителей |

Если пользователь не дал код проекта, попросите версию IPS, место выполнения и фрагмент `.csproj`
с `TargetFramework`. Для сценария достаточно явно подтвердить, что это Script Pad, Workflow,
планировщик или генерация документа.

## 2. Порядок оптимизации

### 2.1. Зафиксируйте измерение

До изменения определите:

- репрезентативный объём: число объектов, связей, атрибутов и строк документа;
- общее время и время крупных фаз;
- количество обращений к IPS/БД, если его можно посчитать;
- объём результата и критерий его эквивалентности;
- расположение выполнения: клиент или сервер.

Для крупной фазы достаточно `Stopwatch` и счётчиков. Не логируйте секреты или содержимое
закрытых объектов. Не называйте процент ускорения без одинакового входа и замеров до/после.

### 2.2. Уберите N+1 обращения к IPS и БД

Это первый кандидат на оптимизацию. Руководство программиста IPS прямо рекомендует при запросе
состава, применяемости или выборки сразу включать все требуемые колонки. Не получайте сначала только
`ObjectId`, чтобы затем в цикле вызывать `IUserSession.GetObject()` и отдельно читать атрибут каждого
объекта.

При ревью:

1. найдите сетевые/серверные вызовы внутри циклов;
2. определите полный минимальный набор данных для результата;
3. запросите эти поля одной выборкой штатного API IPS;
4. постройте результат по возвращённой таблице/коллекции;
5. если пакетного API в документации нет, не выдумывайте его — покажите ограничение и измерьте
   безопасный вариант.

Не заменяйте N+1 вызовов параллельным N+1: это увеличивает нагрузку и для сценариев запрещено.

### 2.3. Используйте кэш метаданных IPS

- Идентифицируйте типы объектов, связей и атрибутов по GUID, а локальные ID получайте через
  `MetaDataHelper`; для сценариев используйте `ScriptContext.MetaDataHelper`, как требует руководство.
- Если один ID нужен много раз в одном выполнении, получите его один раз и храните в локальной
  переменной. Не заводите изменяемый статический кэш в сценарии.
- Не вызывайте полную синхронизацию `MetaDataHelper` вручную на каждом проходе. Она нужна только при
  подтверждённом изменении метаданных.

`MetaDataHelper` уменьшает повторные обращения к БД и является штатным кэшем IPS, а не самодельной
оптимизацией.

### 2.4. Сократите повторную обработку коллекций

После устранения дорогих вызовов проверьте локальный код:

- для многократного поиска по ключу один раз постройте `Dictionary<TKey, TValue>`;
- для проверки принадлежности используйте `HashSet<T>` вместо повторного линейного поиска;
- не выполняйте одинаковые `Where`, `GroupBy`, сортировку или `ToList()` внутри цикла;
- материализуйте последовательность только когда она действительно перечитывается или изменяется;
- не сортируйте данные, если порядок не нужен формату результата;
- сохраняйте читаемость: одна лишняя небольшая коллекция лучше сложного кода без измеримого выигрыша.

### 2.5. Сохраняйте корректные границы записи

- Не меняйте бизнес-транзакцию только ради скорости без проверки семантики.
- Открытая транзакция должна завершиться `Commit` или `Rollback`; для сценариев используйте
  `try/catch/finally` в соответствии с документацией IPS.
- Не распараллеливайте checkout/checkin, создание связей или запись атрибутов: права, рабочие копии,
  уникальность и порядок могут сделать результат недетерминированным.
- Для массовых изменений сначала предусмотрите сухой прогон/preview, идемпотентность и отчёт об
  ошибках. Не удерживайте огромную транзакцию без подтверждённой необходимости.

### 2.6. Оптимизируйте память только после измерения

Из внешнего профиля `csharp-developer` полезны дисциплина профилирования, сокращение лишних
материализаций и выбор подходящих структур данных. Приёмы `Span<T>`, `Memory<T>`, `ArrayPool<T>`,
`ValueTask`, SIMD, source generators, AOT и trimming не являются значениями по умолчанию для IPS:

- в Script Pad они могут быть недоступны или бессмысленны относительно стоимости IPS API;
- в клиентском `net48` часть API отсутствует либо требует дополнительных пакетов;
- в серверном `net6.0` применять их можно только к подтверждённому CPU/allocations hotspot и после
  benchmark-проверки совместимости.

Не добавляйте зависимость или сложную абстракцию ради микровыигрыша.

## 3. Асинхронность и параллелизм

### Сценарии IPS

Не используйте `Task`, `async/await`, `ThreadPool`, `Timer`, Parallel LINQ и фоновые потоки. IPS очищает
объект и изолированное окружение сразу после `Execute`; фоновые операции нарушают жизненный цикл и
официально запрещены. Не подписывайтесь на события клиента/сервера.

### Модули IPS SDK

Асинхронность рассматривайте только после проверки:

1. целевого framework;
2. наличия асинхронного метода в подтверждённом IPS API;
3. потокобезопасности сессии и объектов IPS;
4. механизма отмены и завершения модуля;
5. поведения исключений и транзакции.

Не оборачивайте синхронный IPS API в `Task.Run` ради видимости асинхронности.

## 4. Формат ответа на ревью

1. **Контекст** — версия IPS, Script Pad/Workflow/SDK, клиент/сервер, target framework.
2. **Узкое место** — конкретный цикл, вызов или материализация; фактическое либо гипотеза.
3. **Минимальная правка** — совместимый код без неподтверждённых API.
4. **Почему быстрее** — например, `N` обращений к IPS заменены одной выборкой; сложность поиска
   уменьшена с `O(n²)` до `O(n)`.
5. **Корректность и риски** — права, транзакции, порядок, память, версия API, побочные эффекты.
6. **Проверка** — одинаковый набор данных, результат до/после, время фаз и число вызовов.

Если кода или замеров недостаточно, сначала запросите минимальный воспроизводимый фрагмент и цифры.
Не переписывайте весь сценарий «на современный C#» без подтверждённой причины.

## 5. Контрольный список перед выдачей кода

- [ ] Хост и target framework подтверждены.
- [ ] Использованы только подтверждённые классы и методы IPS.
- [ ] В сценарии нет запрещённой фоновой/асинхронной работы и изменяемого `static`.
- [ ] Нет `GetObject`/чтения атрибутов по одному элементу, если штатная выборка может вернуть колонки.
- [ ] Метаданные читаются через `MetaDataHelper`, GUID не заменены локальными ID из чужой базы.
- [ ] Повторные поиски не образуют очевидное `O(n²)`.
- [ ] Транзакции, cleanup и обработка ошибок сохранены.
- [ ] Побочные эффекты и права указаны.
- [ ] Есть способ сравнить результат и время до/после.
- [ ] Заявленный выигрыш подтверждён замером либо честно назван гипотезой.
