1 Введение
В данном руководстве приводится описание процесса миграции данных из баз Windows-версий
программных комплексов Интермех (Search, IMBASE, Techcard, ImProject) в базу данных IPS. Для
автоматизации процесса миграции предназначена утилита Intermech.ImpExp.Manager.exe, которая находится
в корневом каталоге клиентской части IPS. Для работы данной утилиты требуется подключение к серверу
приложений IPS, а также непосредственно к базам данных Search (ImProject), IMBASE (Techcard) и ко всем
файловым шкафам Search. В связи с этим на компьютере, на котором будет использоваться данная утилита,
должна быть установлена клиентская часть той СУБД, которая используется у вас для хранения данных
Windows-версий программ Интермех.
Следует отметить, что перекачка данных может быть осуществлена между любыми СУБД, которые
поддерживаются программными продуктами Интермех. Например, из Windows-версий Интермех под
InterBase можно перенести данные в IPS под управлением СУБД Oracle или MS SQL Server. Информацию о
версиях СУБД, которые поддерживает установленная у вас версия IPS, смотрите в руководстве по установке
IPS.
Процесс переноса данных может занять длительное время, поэтому рекомендуется проводить его на
выделенном сервере, который может работать круглосуточно. Для проверки правильности переноса данных
следует сначала провести тестовый прогон всей процедуры миграции и проверить работоспособность
полученной базы данных в IPS. Инкрементальный перенос данных не поддерживается, поэтому перед
повторной миграцией данных следует восстановить страховую копию базы IPS, сделанную перед началом
переноса информации. Сам процесс переноса данных можно прерывать – при повторном старте утилиты
миграции данных она предложит продолжить перенос данных. Однако возобновление переноса данных
следует производить на том же сервере и из того же каталога, т.к. там сохраняется информация, необходимая
для продолжения процесса (см. главу 4 ).
Внимание! Сервер приложений IPS и программа миграции должны быть запущены на одном и том же
компьютере. Исходные базы данных и база данных IPS могут располагаться где угодно. Имя папки с
установленным SEARCH должна называться «SEARCH», а папка с IMBASE – IM-BASE».

2 Общие сведения о миграции
В случае проведения обновления программного обеспечения Search, Techcard и Imbase на новую платформу
IPS, которая построена с использованием .NET технологий потребуется так же, как и в случае с простым
обновлением версий произвести миграцию данных.
В отличие от миграции с версии на версию в рамках одной платформы (например, Search v.12 на Search
v.16; Techcard v.9 на Techcard v.12), межплатформенная миграция данных представляет собой сравнительно
сложный и трудоемкий процесс, который требует точного исполнения требований и рекомендаций.
Для простоты понимания миграции введем понятие исторической и целевой системы. Под исторической
системой будем понимать АСУ КТПП, созданную на базе программных продуктов Search, Techcard и Imbase,
под целевой системой – АСУ КТПП на базе Intermech Professional Solutions (IPS).
В процессе миграции происходит перенос из одной системы в другую информации, которую необходимо
условно разделить на метаданные и собственно сами данные.
К метаданным в случае с межплатформенной миграцией будем относить различные атрибуты, типы связей,
типы объектов, типы документов, архивы, действия и переменные бизнес-процессов, понятия Techcard, поля
таблиц Imbase и их типы, а также другую аналогичную информацию. Т.е. сущности, которые непосредственно
не относятся к самой конструкторской, технологической и прочей документации, размещенной на хранение
в Search, Techcard и Imbase, а описывают их в информационной системе (описательная часть информации).
Все что относится к содержательной части информации, размещенной в исторической системе, в виде
отдельных документов (конструкторских, технологических и других), объектов Search и Techcard, шаблонов
бизнес-процессов, таблиц Imbase, эскизов и т.д. будем относить к данным.

3 Конфигурация программы миграции
Файл конфигурации Intermech.ImpExp.Manager.cfg представляет собой xml-файл, содержит информацию,
необходимую для работы программы миграции, и состоит из следующих секций:
1. Секция Plugins. В этой секции определены относительные пути к файлам адаптеров (названия
файлов Intermech.ImpExp.Adapter*.dll) и модулям расширений (плагинам).
Адаптеры необходимы для работы с различными СУБД. В модулях расширения реализован весь
функционал программы миграции по чтению, обработке, настройке и импорту данных из Imbase, Search и
TechCard.
2. Секция TempFolders. Указаны относительные пути и названия каталогов, в которых будут
храниться файлы настройки миграции данных и кэша импортированных данных.
3. Секция DBConfigs. Содержит настройки, определяющие параметры работы с базой данных IPS:
 DropIndexes, флаг удаления индексов, при установке в значении True в начале процесса
миграции данных в таблицах базы назначения будут удалены некоторые индексы для
повышения скорости вставки данных. В конце миграции индексы будут восстановлены. Этот
режим рекомендуется использовать только при очень больших объемах переносимой
информации. По умолчанию флаг установлен в значение False.
4. Секция FormStorage. В этой секции программа миграции сохраняет значения для форм
(положение, размер и т.д.). Информация системная, править не рекомендуется.
<?xml version="1.0"?>
<Settings>
<Plugins>
<!-- Адаптеры работы с базами данных -->
<Plugin LOCATION="Intermech.ImpExp.Adapter.Interbase.dll" />
<Plugin LOCATION="Intermech.ImpExp.Adapter.MsSQL.dll" />
<Plugin LOCATION="Intermech.ImpExp.Adapter.Oracle.dll" />
<!-- Плагины -->
<Plugin LOCATION="Intermech.ImpExp.Imbase.dll" />
<Plugin LOCATION="Intermech.ImpExp.Search.dll" />
<Plugin LOCATION="Intermech.ImpExp.SearchData.dll" />
<Plugin LOCATION="Intermech.ImpExp.TechCard.dll" />
<Plugin LOCATION="Intermech.ImpExp.Workflow.dll" />
</Plugins>
<TempFolders>
<!-- Относительный путь к каталогу с файлами кэша -->
<TempFolder NAME="Cache" LOCATION="ImpExpTemp" />
<!-- Относительный путь к каталогу с файлами настроек -->
<TempFolder NAME="Settings" LOCATION="ImpExpTemp" />
</TempFolders>
<DBConfigs>
<!-- Флаг удаления индексов -->
<DBConfig NAME="DropIndexes" VALUE="False" />
</DBConfigs>
</Settings>

4 Восстановление работы программы после сбоя
После падения программы в результате какого-либо внешнего воздействия или внутренней ошибки
предусмотрен механизм восстановления. На схеме условно представлен процесс миграции во времени. При
последующих после сбоя запусках программы, если будет обнаружена точка восстановления, программа
предложит продолжить с места сохранения последней точки восстановления. Если же точки восстановления
обнаружено не будет, то программа будет запущена с самого начала.
Pump 1, Pump 2 … Pump N – части импорта данных. Каждая часть производит импорт определенного вида
данных. Т1, Т2 … Тn – точки восстановления.
Первым этапом миграции идут шаги по настройке импорта. После выполнения каждого шага по настройке
результаты сохраняются на диск. Сохранение файлов с настройками, а также файлов кэша производится в
папки, указанные в файле конфигурации в секции TempFolders. Если же после сбоя, на первом шаге нажать
на ссылку , то существующие настройки будут затерты.
В процессе работы программы автоматически на диск записывается несколько точек восстановления.
Первая точка восстановления будет создана после завершения этапа Импорт метаданных (на схеме Т1). Все
последующие точки восстановления будут автоматически записаны после выполнения каждой из частей
импорта данных.
Во время импорта данных на дисковый кэш производится запись информации об уже импортированных
данных, которая учитывается при восстановлении после сбоя. Эту информацию можно удалить, нажав на
первом шаге на ссылку .
Таким образом программа миграции может восстановить свое состояние после сбоя с точностью до
единицы импортируемой информации.

5 Просмотр информационных сообщений и ошибок
В процессе настройки, обработки или импорта данных все информационные сообщения, ошибочные и
исключительные ситуации выводятся в нижней части окна программы в виде списка. Все находящиеся в
списке записи дублируются в лог-файл import.log на стороне клиента, в папке исполняемого файла
программы.
Все сообщения, выдаваемые программой миграции, делятся на 3 категории:
 Критические ошибки.

7.1 Ключевые особенности процесса нормализации БД Imbase
При отработке процесса нормализации БД Imbase необходимо учесть некоторые особенности модели
хранения данных в БД Imbase и БД Imbase IPS.
1. В БД Imbase IPS (и в целом в системе IPS) уникальность атрибута отслеживается по длинному
имени без учета регистра.
Например, в БД Imbase присутствуют 10 полей с именем Длина. Три из них с коротким именем l,
три с коротким L и остальные без короткого имени. При миграции таких данных в Imbase IPS
программа миграции создаст в IPS три атрибута с короткими именами L, l и без короткого имени
(наличие коротких имен необходимо для системы Cadmech и других программ комплекса ПО
ИНТЕРМЕХ). Но, так как три атрибута Длина в IPS быть не может, то длинное имя сформируется
в IPS как Длинное имя + короткое имя, а для различий Длина l и Длина L, перед символами
короткого имени в верхнем регистре добавляется символ ^. Таким образом в IPS получатся Длина
l и Длина ^L. В дальнейшем такие имена атрибутов могут быть переименованы непосредственно
в IPS на этапе дальнейшей настройки системы IPS.
2. Поля с одинаковым длинным и коротким именем во всех таблицах БД Imbase должны быть
совместимого типа. Данное условие обеспечивает целостность данных в процессе миграции.
Ситуации, когда поле в разных таблицах БД Imbase может быть строковым, целым и вещественным
приводят к потере данных при миграции.
44 Intermech Professional Solutions 9.0

Например, поле Длина с коротким именем l во всех таблицах должно быть целого или
вещественного типа.
3. Наличие единиц измерения для поля в БД Imbase подразумевает, что тип поля должен быт
числовым (целым или вещественным). Строковые поля с единицей измерения считаются не
допустимыми для системы IPS. Единицу измерения необходимо убрать или перевести данные в
числовой тип.
4. Программа IPS не допускает назначения двух разных типов данных для одного атрибута.
5. При миграции в БД Imbase IPS данных из таблиц БД Imbase, имеющих поля с единицей измерения,
необходимо чтобы по всем таблицам в БД Imbase у таких полей были назначены единицы
измерения.

Пример: Не удалось добавить значение по-умолчанию «2,1-2,2» к атрибуту ПЛОТНОСТЬ1 q1 таблицы

double (число с плавающей запятой), указанное в Imbase, как значение по-умолчанию. Значение по-
умолчанию для нового атрибута не установлено. Рекомендуется уточнить значение и установить его вручную.
Пример: Блоб TC101297.DWG не импортирован, так как его размер (1136422 байт) больше чем допустимый
размер короткого блоба (262144 байт).

производится запись. Необходимо определить, в какой атрибут IPS производится запись и увеличить его
максимальный размер. Следует помнить, что максимальный размер атрибута типа Короткие двоичные
данные составляет 256 Кбайт. В данном примере ошибка произошла при выполнении задачи Перекачка
изображений Imbase. В этом случае файлы записываются в атрибут LIBRARY_IMAGE. Если самостоятельно
определить атрибут, обратитесь в службу поддержки.

Рекомендуется после окончания работы программы миграции установить пользователю новый пароль в IPS
в Администраторе базы данных (см. п. 4.5.1 Пользователи и группы пользователей в «Руководстве
администратора»).
Пример: Ошибка при перекачке информации о внешней программе 18760 (таблица EXTENS): Настройки
команды не содержат названия приложения.
Комментарий: Информация о внешней программе не содержит названия приложения. Рекомендуется
установить название для внешней программы в исходном приложении перед следующей закачкой.
Пример: Ошибка при перекачке информации о внешней программе 8093 (таблица EXTENS): Не задана
команда реестра, используемая для запуска приложения.
Комментарий: Информация о внешней программе не содержит команды реестра, используемой для
запуска приложения. Рекомендуется установить недостающую информацию для внешней программы в
исходном приложении перед следующей закачкой.
Пример: Не указан тип для идентификатора внешней программы 85 (таблица EXTENS).
Комментарий: Для внешней программы в исходной базе не указан тип запуска. Допустимые типы запуска
приложений должны быть:
 0 – запуск приложения производится по указанному исполняемому файлу.
 1 – запуск приложения производится по указанной в реестре информации.
Рекомендуется исправить некорректную информацию в исходной базе перед следующей закачкой.
Пример: Неверный тип 3 внешней программы 19859 (таблица EXTENS).
Комментарий: Для внешней программы в исходной базе указан недопустимый тип запуска. Допустимые
типы запуска приложений должны быть:
 0 – запуск приложения производится по указанному исполняемому файлу.
 1 – запуск приложения производится по указанной в реестре информации.
Рекомендуется исправить некорректную информацию в исходной базе перед следующей закачкой.
Пример: Объект IMBASE c hash = «7005091659777» не найден в кэше импортированных объектов (Код
таблицы = «1631» код записи = «1»)
Комментарий: В таблице ЭС присутствует ссылка на несуществующую папку каталога/справочника
Imbase. Рекомендуется внести исправления в исходной базе.
Пример: Неверный аргумент. Не найден атрибут для понятия (Уд_В) ( понятие отсутствует в настройках ).
Комментарий: Для понятия установлен режим перекачки – Не качать. Для всех понятий типа Без
сохранения в ТП – данное сообщение игнорировать.
Пример: Ошибка создания элемента формулы. Понятие = ШАГр.
Комментарий: Не удалось конвертировать понятие в соответствующий атрибут IPS при перекачке
формул/условий ЭС. Проверить настройки перекачки понятия.
Пример: Невозможно изменить атрибут Ссылка на объект IMBASE в контексте типа Оснастка для
понятия «%osn»: Нет доступа на редактирование этого атрибута
Комментарий: Атрибут Ссылка на объект IMBASE в IPS является системным (защищен от изменения).
Данное сообщение игнорировать
