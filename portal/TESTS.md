# TESTS — автотесты портала

## Запуск

```powershell
cd D:\parsing\IPS-Durdom-5\ips-helper-suite-5\portal
npm test
# без npm:
node --test "test/**/*.test.ts"
```

Текущий результат: **32 теста, 32 пройдено, 0 провалено**.

Тесты **не трогают** живой OpenCode: поднимается mock-сервера
`test/mock-opencode.ts`, реализующая ровно те маршруты v2, которые использует
портал (формы запросов и ответов — как в OpenAPI живого сервера 2.1.2).
Сам портал поднимается на случайном порту в том же процессе (`test/harness.ts`).

```
test/
  harness.ts        запуск портала против mock-сервера, вспомогательные функции
  mock-opencode.ts  mock API OpenCode v2 (сессии, агенты, модели, SSE, разрешения)
  portal.test.ts    изоляция пользователей, запрет маршрутов, файлы, разрешения, SSE
  config.test.ts    конфигурация и срок хранения
```

## 1. Что именно проверяется

### 1.1. A не видит сессию B

`portal.test.ts` → **«A не видит сессии B: list, messages, events, delete, files»**

Сессия создаётся пользователем `user-b`, затем пользователь `user-a` проверяет
**каждый** маршрут:

| Проверка | Запрос `user-a` | Ожидается |
|---|---|---|
| list | `GET /api/sessions` | id сессии B **отсутствует** в выдаче |
| get / messages | `GET /api/sessions/{id}/messages` | **404** |
| events | `GET /api/sessions/{id}/events` | **404**, и поток **не открывается** (в ответе нет `text/event-stream`) |
| files (список) | `GET /api/sessions/{id}/files` | **404** |
| files (скачивание) | `GET /api/sessions/{id}/files/report.md` | **404** |
| delete | `DELETE /api/sessions/{id}` | **404**, сессия у B остаётся целой |

Отдельный тест **«чужая сессия не отдаёт события»** проверяет, что при 404
поток не открывается: заголовок `Content-Type` не содержит `text/event-stream`.

Плюс **«A не видит сессии B»** в обратную сторону: у `user-b` та же сессия
по-прежнему читается (200) — изоляция не ломает владельцу.

### 1.2. Запрещённые маршруты

**«запрещённые маршруты не пробрасываются»** — 49 путей, каждый должен дать 404:

* маршруты v2: `/api/project`, `/api/config`, `/api/credential`, `/api/integration`,
  `/api/provider`, `/api/mcp`, `/api/session`, `/api/session/active`,
  `/api/session/{id}/shell`, `/api/session/{id}/command`, `/api/session/{id}/inbox`,
  `/api/fs/list`, `/api/fs/find`, `/api/fs/read/secret.txt`, `/api/pty`,
  `/api/plugin`, `/api/worktree`, `/api/vcs/status`, `/api/command`, `/api/skill`,
  `/api/rpc/{id}/{method}`, `/api/reference`, `/api/shell`, `/api/form`,
  `/api/permission/request`, `/api/permission/saved`, `/api/websearch`,
  `/api/debug/location`, `/api/experimental/migration/v1`, `/api/experimental/generate`,
  `/api/model/default`, `/api/agent/{id}`;
* маршруты v1 из ТЗ: `/project`, `/project/current`, `/config`, `/config/providers`,
  `/auth/{id}`, `/provider`, `/mcp`, `/instance/dispose`, `/session`,
  `/session/status`, `/session/{id}/shell`, `/file`, `/file/content?path=…`,
  `/find/file?query=*`, `/tui/append-prompt`, `/global/event`.

**«портал вызывает только разрешённые маршруты OpenCode»** — mock-сервер
записывает **каждый** фактический вызов портала; тест сверяет их с
whitelist-регексом:

```
/api/agent
/api/model
/api/session
/api/session/{id}
/api/session/{id}/message
/api/session/{id}/prompt
/api/session/{id}/agent
/api/session/{id}/permission
/api/session/{id}/permission/{id}/reply
/api/experimental/session/{id}/instructions/entries/{key}
/api/event
```

Это защита от «случайно проксировать» — регрессия валит тест.

### 1.3. Недопустимая модель

**«недопустимая модель отклоняется»**: `POST /api/sessions` с
`{"agent":"ips-help","model":"opencode/not-allowed-model"}` → **400**,
`error.code = "model_not_allowed"`, перечисление разрешённых моделей в тексте
ошибки. Модель `opencode/not-allowed-model` существует в mock-модели OpenCode —
то есть проверяется именно белый список портала, а не наличие модели.

Дополнительно **«неизвестный агент отклоняется»** → 400 `unknown_agent`.

### 1.4. Запрос разрешения получает автоматический отказ

**«запрос разрешения получает автоматический отказ»**:

1. владелец открывает `GET /api/sessions/{id}/events` (SSE);
2. mock поднимает запрос разрешения и публикует событие `permission.asked`;
3. портал отвечает сам:
   `POST /api/session/{id}/permission/{requestID}/reply` с `decision = "reject"`
   и непустым сообщением;
4. пользователь в чате получает событие `portal.permission.rejected` с понятным
   текстом (проверяется регуляркой `/отклон/i`).

**«запрос разрешения обрабатывается даже без активного слушателя»** — тот же
сценарий без подключённого SSE-клиента: отказ всё равно уходит (значит, отказ
не зависит от того, смотрит ли кто-то в чат).

Дополнительно код покрыт периодическим опросом
(`GET /api/session/{id}/permission` раз в 30 секунд) — он нужен, потому что
поток событий OpenCode **volatile** и не переигрывает пропущенное.

### 1.5. Скачивание файлов

**«скачивание файла сессии работает и отдаётся как вложение»**
— файл `report.md` в `output\<id>\` отдаётся с кодом 200, телом ровно как на
диске и заголовком `Content-Disposition: attachment; …`.

**«обход пути при скачивании отклоняется»** — файл `secret.txt` лежит **вне**
папки сессии (в её родителе). Проверяются:

| Попытка | Результат |
|---|---|
| `files/..%2Fsecret.txt` | 400/404, содержимое не утекает |
| `files/..%2F..%2Fsecret.txt` | 400/404, содержимое не утекает |
| `files/%2e%2e%2fsecret.txt` | 400/404, содержимое не утекает |
| `files/%2e%2e%2f%2e%2e%2fsecret.txt` | 400/404, содержимое не утекает |
| **необработанный** `files/../secret.txt` (сырой HTTP-запрос, без нормализации URL клиентом) | 400/404, содержимое не утекает |

Последний случай отправляется «сырым» `node:http`, потому что `fetch`
нормализует `..` ещё до отправки — это артефакт клиента, а не сервера.

**«абсолютный путь при скачивании отклоняется»** — `files/C%3A%5CWindows%5Cwin.ini` → 400/404.

**«недопустимое расширение отклоняется»** — `payload.exe` и `secret.env`:
оба дают **400** с `error.code = "extension"`, и в списке файлов их тоже нет.

**«симлинк наружу отклоняется»** — символическая ссылка `link.md` внутри папки
сессии на файл снаружи: 400/404, содержимое цели не утекает.

**«файл больше лимита не отдаётся»** — при `files.maxBytes = 10` файл из 100
байт даёт **413**.

## 2. Живая проверка на реальном OpenCode

Автотесты работают против mock-сервера. Отдельно (вручную, при ручном
запуске портала) проверено на живом `opencode serve --service`:

| Проверка | Результат |
|---|---|
| `GET /api/agents` без `X-User` | 401 |
| `GET /api/agents` с `X-User` | список первичных агентов проекта с описаниями |
| `POST /api/sessions` | создана сессия `ses_…`, модель `mimo-v2.6-flash-free` / `providerID=opencode` |
| instruction entry в OpenCode | ключ `portal-output`, текст правила на русском в правильной кодировке, содержит абсолютный путь и `output\<id>\` |
| `GET /api/sessions/:id/files` | `{"data":[]}` (файлов ещё нет) |
| `GET /api/project` (запрещённый) | 404 |
| `GET /session` (запрещённый, имя v1) | 404 |
| фронтенд `/`, `/app.js`, `/styles.css` | 200 |
| `DELETE /api/sessions/:id` | сессия и папка `output\<id>` удалены |

## 3. Что тестами **не** покрыто (и почему)

| Область | Почему |
|---|---|
| Реальный ответ модели MiMo (стриминг, качество) | требует денег/квоты и живого сервера; логика показа покрыта mock-событиями |
| Реальный MCP `ips` (база IPS) | конфигурация V1 не менялась, MCP остаётся на стороне OpenCode |
| AD/SSO | сейчас заглушка `X-User`; интерфейс `AuthProvider` рассчитан на замену |
| Поведение при падении OpenCode (переподключение SSE) | реализовано (экспоненциальный backoff, пере-определение адреса), но требует живой инъекции сбоев |
| Нагрузка | `limits.*` покрыты функционально, но нагрузочного стенда нет |
